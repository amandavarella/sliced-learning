Overview

This page walks a new team member through the reading service, a small fictional service that turns long documents into short sections. It exists only to exercise the Sliced Learning extractor, so every name, number and person on it is made up. The page is long enough to slice into more than one section, which is why some paragraphs repeat the same ideas in slightly different words.

Current status: IN PRODUCTION and the migration is IN PROGRESS. Questions go to the team channel and the tracking ticket is READ-42 - Move the reading service to the new cluster In Progress.

Before you start

You need access to the staging account and a local copy of the repository. Ask your onboarding buddy if either is missing on your first day.

Architecture

The service has three parts: a fetcher that downloads a document, a slicer that cuts it into sections of about four hundred words, and a store that keeps the sections and the reading progress for each person. The fetcher and the slicer run in the same process. The store is a managed database, so there is nothing to operate there beyond watching the storage graph once a week.

Requests arrive through the public load balancer and reach the fetcher first. When a document is already in the store, the fetcher skips the download and the slicer reads the stored copy instead, which keeps repeat requests fast. When the document is new, the fetcher stores the raw copy before the slicer starts, so a crash in the slicer never loses the download.

Local setup

Clone the repository, install the dependencies and start the service with the development configuration. The first start downloads a small sample of documents so the slicer has something to work on. It takes about two minutes on a normal connection, and later starts reuse the sample.

Start the service locally
git clone https://example.com/reading-service.git
cd reading-service
npm install
npm run dev -- --config config/development.json

When the service is up, open the local address in a browser and paste the link to any public article. The slicer prints one line per section to the terminal, with the word count, so you can check the cut points while you work on them.

Troubleshooting the first start

If the sample download fails, check that the proxy settings in your shell match the ones in the development configuration. A stale lock file from an earlier run also stops the start; delete it and try again. If neither helps, ask in the team channel with the last twenty lines of the log.

Release checklist

Every release follows the same short checklist. It is written down here because the steps are easy to skip on a busy day, and each one has caught a real problem at least once.

  1. Run the full test suite and the slicer comparison against the saved sample.

  2. Read the diff of the configuration files, not just the code.

  3. Deploy to staging and slice three long documents by hand.

  4. Watch the error graph for ten minutes after the production deploy

Never deploy on the last working day before a holiday. The on-call rota is thin, and a slow rollback is much worse than a release that waits a few days.

After the release, update the changelog page and close the release ticket. If anything went wrong, write a short note on the incident page while the details are fresh, even when the problem was small. These notes are how the checklist above grew, and the next person to join the team will read them during their first week, the same way you are reading this page now.
